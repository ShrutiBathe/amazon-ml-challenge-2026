# Amazon ML Challenge 2026 — Entity Resolution & Record Linkage

## Team Insight-X

An end-to-end machine learning pipeline for resolving business entities across heterogeneous data sources. The system identifies records in Source 2 and Source 3 that correspond to each Source 1 entity despite variations in business names, addresses, country representation, formatting, and noisy records.

---

## 1. Problem Overview

Entity resolution, also known as record linkage, is the process of determining whether records from different datasets refer to the same real-world entity.

For this challenge, Source 1 acts as the reference entity dataset, while Source 2 and Source 3 contain noisy representations of the same or different entities.

The system must determine, for every Source 1 entity:

- Whether matching records exist in Source 2 and/or Source 3
- Which records correspond to the same entity
- Whether there are multiple valid matches
- Whether the entity has no matching record

The solution is designed to handle large-scale datasets without performing an exhaustive comparison between every possible record pair.

## 2. System Architecture

The solution follows a four-stage pipeline:

```text
Raw Data
   │
   ▼
┌──────────────────────┐
│ M1: Preprocessing    │
│ Normalization        │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│ M2: Candidate        │
│ Generation / Blocking│
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│ M3: ML Matching      │
│ Random Forest        │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│ M4: Final Decision   │
│ Threshold + Mapping  │
└──────────┬───────────┘
           │
           ▼
    Final Entity Mapping

The important design principle is that the candidate set generated by M2 is retained as the evidence base for M3 scoring and M4 decision-making.

3. Modules
M1 — Data Preprocessing

M1 converts heterogeneous raw records into standardized representations.

Main operations include:

Unicode normalization
Lowercase conversion
Punctuation normalization
Conversion of & to and
Whitespace normalization
Compact text representations
Legal business suffix removal
Duplicate-token normalization
Name prefix extraction
First-token extraction
Address normalization
Address token extraction
Country normalization

These transformations reduce superficial differences while preserving information useful for matching.

M2 — Candidate Generation / Blocking

Comparing every Source 1 record with every Source 2 and Source 3 record would create an impractical search space.

M2 therefore uses blocking strategies to generate a smaller set of plausible candidate pairs.

The blocking design uses complementary signals such as:

Exact normalized business name
Name prefix
First name token
Address token
Address first token
Country-aware blocking

Candidate pairs are deduplicated using:

(source1_entity_id, candidate_source, candidate_entity_id)

This ensures that the same candidate is processed only once even if multiple blocking strategies identify it.

Candidate generation is performed using disk-backed/chunk-based processing to reduce memory pressure on the large datasets.

M3 — Machine Learning Matching

M3 evaluates the candidate pairs generated by M2.

For each candidate pair, the system constructs a multi-signal feature vector containing information such as:

Name Features
Exact normalized-name match
Exact compact-name match
Name after suffix removal
Duplicate-token similarity
Token Jaccard similarity
Containment
Character similarity
Length differences
Token-count differences
Prefix agreement
Address Features
Exact address match
Address Jaccard similarity
Address containment
Character similarity
Numeric overlap
Numeric conflict
Address token information
Country Features
Country agreement
Country conflict
Evidence Features
Supporting evidence
Contradictory evidence
Combined signal indicators

The resulting feature representation is used by a Random Forest classifier to estimate the probability that a candidate pair represents the same entity.

The model configuration used in the project is:

Algorithm : Random Forest
Trees     : 300
Features  : 34
M4 — Final Decision

M4 converts the probabilities generated by M3 into final entity mappings.

The decision stage:

Reads candidate-pair probabilities.
Applies the selected probability threshold.
Groups accepted matches by Source 1 entity.
Retains multiple valid matches where applicable.
Produces the final submission files.

The system does not assume a strict one-to-one relationship because the challenge ground truth contains Source 1 entities with zero, one, or multiple matches.

4. Dataset Characteristics

The training ground truth contains:

2,206,821 Source 1 records
123,247 Source 1 records with no match
1,964,417 Source 1 records with multiple matches

The no-match proportion is approximately 5.58%.

Noise analysis showed that no individual attribute is sufficient for reliable entity resolution. For example, exact normalized names and exact addresses cover only a portion of true matches, motivating the use of multiple complementary signals.

5. Output Files

The final system produces two TSV files.

matching_results.tsv

Contains one row for every Source 1 entity.

Expected columns:

source1_entity_id
matched_entity_ids

matched_entity_ids may contain:

Empty value — no match
One entity ID — single match
Multiple comma-separated entity IDs — multiple matches

Example:

source1_entity_id    matched_entity_ids
S1_001               S2_102,S3_884
S1_002
S1_003               S2_551
candidate_pairs.tsv

Contains the candidate evidence set used by the matching pipeline.

Expected columns:

source1_entity_id
candidate_entity_ids

Example:

source1_entity_id    candidate_entity_ids
S1_001               S2_102,S2_551,S3_884
S1_002
S1_003               S2_771

Every final match appearing in matching_results.tsv must also exist in the corresponding candidate list.

10. Design Principles
High Recall Candidate Generation

M2 is designed to preserve plausible true matches while significantly reducing the number of comparisons.

Multi-Signal Matching

The system does not rely on a single field. Business name, address, country, token-level and character-level similarities are combined.

Multiple-Match Support

The system supports:

Source 1 → 0 matches
Source 1 → 1 match
Source 1 → multiple matches
Country-Agnostic Processing

Country is treated as a normalized feature rather than relying on country-specific hard-coded logic.

Scalable Processing

Large datasets are processed in chunks and intermediate candidate data can be stored on disk rather than requiring the entire candidate space to remain in memory.

Traceable Candidate Evidence

The candidate set used for ML scoring is preserved so that final predictions can be traced back to the candidates considered by the system.

11. Evaluation

The system is evaluated using the challenge's entity-resolution scoring methodology.

Important evaluation considerations include:

Precision of predicted matches
Recall of true matches
F-beta based evaluation
Correct handling of no-match entities
Correct handling of multiple matches
Candidate recall
Validity and completeness of submission files

Because the challenge uses a precision-oriented F-beta configuration, the final decision stage is designed to avoid accepting weak candidate pairs indiscriminately.

13. Conclusion

This project implements a scalable entity-resolution pipeline combining data normalization, blocking, feature engineering, machine learning, and final decision processing.

The M1 → M2 → M3 → M4 architecture separates preprocessing, candidate generation, learned matching, and final decision-making, allowing the system to process large heterogeneous datasets while supporting zero, single, and multiple entity matches.
